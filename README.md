## 3. 주요 실습 내용
- 데이터 조회: `SELECT`, `ORDER BY`, `LIMIT` 으로 명세서 훑어보기
- 조건 검색: `WHERE`, `BETWEEN`, `LIKE`, `IN`, `IS NOT NULL`
- GROUP BY: 종별·상병별·병기별 집계, `HAVING` 으로 그룹 거르기
- JOIN: 명세서 + 상병마스터 + 요양기관 + 코드표 다중 조인, 사망 기록을 붙이는 `LEFT JOIN`
- 데이터 집계: `COUNT`, `COUNT(DISTINCT)`, `SUM`, `AVG`, 비율 계산
- 윈도우 함수: `ROW_NUMBER`, `LAG`, 누적 `SUM ... OVER` 로 환자별 방문 순번·간격·누적 진료비
- CTE(`WITH`): 코호트 정의 → 결과(outcome) 계산 → 집계로 단계 나누기
- CASE: 병기값을 4개 그룹으로 묶기, 0/1 플래그로 비율 계산

## 4. 주요 SQL

### 4-1. 환자별 방문 간격 (윈도우 함수 + CTE) — 과제 2 Q3
윈도우 함수는 `WHERE` 보다 나중에 계산되므로 `WHERE` 안에서 `LAG` 를 바로 쓸 수 없습니다(ERROR 3593). CTE로 먼저 간격을 계산해 이름을 붙이고 바깥에서 거릅니다.

```sql
WITH v AS (
  SELECT jid, recu_fr_dd,
         ROW_NUMBER() OVER (PARTITION BY jid ORDER BY recu_fr_dd) AS visit_no,
         DATEDIFF(recu_fr_dd, LAG(recu_fr_dd) OVER (PARTITION BY jid ORDER BY recu_fr_dd)) AS gap_days,
         SUM(rvd_rpe_tamt_amt) OVER (PARTITION BY jid ORDER BY recu_fr_dd) AS cum_amt
  FROM claim
  WHERE main_sick = 'E119' AND fom_tp_cd = '031'
)
SELECT * FROM v
WHERE gap_days > 90
ORDER BY gap_days DESC;
```

### 4-2. 병기 그룹별 3년 안 사망률 (CTE + CASE + LEFT JOIN) — 과제 3 Q2
코호트(누구를) → 결과(무슨 일이) → 집계(얼마나) 순서로 CTE를 나눴습니다.
사망 기록이 없는 환자도 분모에 남아야 하므로 `JOIN` 이 아니라 `LEFT JOIN` 을 씁니다.

```sql
WITH cohort AS (
  SELECT pt_sbst_no, bspt_frst_diag_ymd AS index_dd,
         CASE WHEN bspt_stag_vl IN ('0', '1', '2') THEN '1) 초기 (0~2기)'
              WHEN bspt_stag_vl = '3' THEN '2) 국소 진행 (3기)'
              WHEN bspt_stag_vl = '4' THEN '3) 전이 (4기)'
              ELSE '4) 병기 미상' END AS stage_group
  FROM lung_pt_bsnf
  WHERE bspt_frst_diag_ymd >= '2010-01-01' AND bspt_frst_diag_ymd < '2018-01-01'
),
outcome AS (
  SELECT c.pt_sbst_no, c.stage_group,
         CASE WHEN d.dead_ymd <= c.index_dd + INTERVAL 1095 DAY THEN 1 ELSE 0 END AS dead_3y
  FROM cohort c
  LEFT JOIN lung_dead_nfrm d ON d.pt_sbst_no = c.pt_sbst_no
)
SELECT stage_group, COUNT(*) AS patients, SUM(dead_3y) AS dead_3y,
       ROUND(AVG(dead_3y) * 100, 1) AS dead_3y_pct
FROM outcome
GROUP BY stage_group
ORDER BY stage_group;
```

## 5. 문제 해결

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| DBeaver에서 MySQL 연결 실패 (`Public Key Retrieval is not allowed`) | MySQL 8의 기본 인증 방식 | 연결 우클릭 → Edit Connection → Driver Properties → `allowPublicKeyRetrieval` 을 `true` 로 변경 |
| 고혈압 명세서가 0건 (`main_sick = 'I10'`) — 에러 없음 | 데이터에는 세부 코드 `I109` 로 저장됨 | `sick_master` 에서 `LIKE 'I10%'` 로 실제 값을 확인한 뒤 `I109` 사용. 결과가 0행이면 쿼리보다 값부터 확인 |
| `ERROR 1055 ... not in GROUP BY clause` | `only_full_group_by` 모드에서 SELECT에 묶이지 않은 열(`main_sick`)이 있음 | 그 열을 `GROUP BY` 에 넣거나 `COUNT(DISTINCT ...)` 같은 집계 함수로 감쌈 |
| `ERROR 3593 You cannot use the window function 'lag' in this context` | 윈도우 함수는 `WHERE` 이후에 계산됨 | CTE(`WITH v AS (...)`)에서 먼저 계산하고 바깥 쿼리에서 거름 |
| 1년 사망률이 두 배 가까이 높게 나옴 (2010년 31.4% → 48.4%) — 에러 없음 | `JOIN` 이 사망 기록 없는 환자를 통째로 제외해 분모가 8,436명 → 3,293명으로 줄어듦 | `LEFT JOIN` 으로 변경. 단계마다 행 수를 세어 코호트 인원과 맞는지 확인 |
| 병기 그룹이 4개가 아니라 3개, 초기 그룹이 3,813명이 아니라 4,163명 (Warning 1292) | 문자 열 `bspt_stag_vl` 을 숫자와 비교하자 `'x'` 가 0으로 바뀌어 초기 그룹에 섞임 | 문자는 문자로 비교: `IN ('0', '1', '2')`. 합계뿐 아니라 그룹 수와 값별 인원도 함께 확인 |

## 7. 배운 점
- **에러가 안 나도 틀릴 수 있다.** `I10` vs `I109`, `JOIN` vs `LEFT JOIN`, 문자 `'x'` 와 숫자 비교 모두 에러 없이 잘못된 숫자를 냈습니다. 결과가 0행이면 값부터 보고, 단계마다 행 수를 세어 분모가 맞는지 확인하는 습관이 필요합니다.
- **분모에 누가 있는지부터 묻는다.** 비율은 분모가 바뀌면 전혀 다른 이야기가 됩니다. 코호트 범위를 정하고, 그 범위를 결과와 함께 적어야 합니다.
- **쿼리가 질문에 다 답했는지 확인한다.** `LAG` 로 찾은 "90일 넘게 비운 사람"에는 돌아오지 않은 환자가 빠져 있었습니다. 실행 성공과 질문에 대한 답은 다릅니다.
- **SQL 실행 순서를 알면 에러가 읽힌다.** `FROM → WHERE → GROUP BY → HAVING → SELECT(윈도우 함수) → ORDER BY` 순서를 알면 ERROR 1055, 3593 이 왜 나는지 이해됩니다.
- **CTE로 단계를 나누면 읽기 쉽다.** 코호트 → 결과 → 집계로 나누니 긴 쿼리도 중간 결과를 하나씩 확인할 수 있었습니다.
- **청구 데이터와 임상 데이터는 답할 수 있는 질문이 다르다.** 청구 자료는 돈과 방문을, 임상 자료는 진단·치료·사망을 기록합니다.
